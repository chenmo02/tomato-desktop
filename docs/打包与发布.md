# 打包与发布流程

> 适用范围：番茄桌面 Windows x64 单文件程序、NSIS 安装包，以及发布到 GitHub Releases 供客户端在线更新。
> 本文是 [开发与构建](开发与构建.md) 中「构建安装包 / 发行新版本」两节的可执行展开，并以 2026-11-13 发布的 `v1.3.0`、`v1.4.0` 为完整实例。所有命令默认从仓库根目录执行。

## 1. 流程总览

| 步骤 | 动作 | 产物 / 结果 |
| --- | --- | --- |
| 1 | 版本号加一，同步四处定义 | `csproj`、`Installer.nsi`、README 口径一致 |
| 2 | 编写版本说明 | `native/releases/vX.Y.Z.md` |
| 3 | 构建单文件程序 | `native/artifacts/win-x64/TomatoDesktop.exe`（约 142 MB，仅作载荷） |
| 4 | 生成安装包 | `native/artifacts/TomatoDesktop-Setup.exe`（主交付物） |
| 5 | 编译与自检 | 0 警告、核心 33/33、尺寸 60/60、UI 86/86、在线更新专项 7/7 |
| 6 | 发布 Release | 草稿 → 上传两个资产 → digest 校验 → 公开并设为 latest |
| 7 | 发布后核对 | 线上 `latest` 满足客户端全部校验规则；同步提交源码 |

两条硬约束决定后面每个步骤的写法：

1. **tag 由 EXE 版本资源推导，不是由 csproj 的两段版本推导。** `Publish-Release.ps1` 取 `FileVersion` 的前三段生成 `v1.3.0`；客户端 `OnlineUpdater.Parse` 再把 tag 解析成 `Version(1,3,0)` 与本机版本比较，并在下载后要求 EXE 的 `FileVersion` 三段与之相等。
2. **客户端只接受本仓库 `releases/download/` 路径下、带有效 `sha256:` digest 与 `size` 的 `TomatoDesktop-Setup.exe`。** 任一条件不满足，`Parse` / `TrustedUrl` 会抛错并拒绝更新（详见第 6 节）。

## 3. 版本号：唯一来源与同步清单

程序集版本的唯一来源是 `native/DesktopNook.App/DesktopNook.App.csproj` 的 `<Version>`。每次发版必须同步以下位置：

| 文件 | 字段 | v1.3 值 | 作用 |
| --- | --- | --- | --- |
| `DesktopNook.App.csproj` | `<Version>` | `1.3` | 程序集版本、`ProductVersion`、界面显示 `v1.3` |
| `Installer.nsi` | `SETUP_VERSION` | `1.3.0` | 安装器界面、版本资源和 HKCU 卸载登记共用；发布脚本读取版本资源生成 tag |
| `README.md` / `native/README.md` | 版本徽章、当前源码版本 | `1.3` | 文档口径 |
| `MainWindow.xaml.cs` | 版本注释 | 通用表述 | 仅注释，不影响行为 |

`Installer.nsi` 是 **UTF-16 LE 带 BOM**，`*.nsi` 在 `.gitattributes` 中按二进制保存。修改时应按字节替换并保留 BOM 与 CRLF：

```python
from pathlib import Path
p = Path("native/scripts/Installer.nsi")
b = p.read_bytes()
assert b[:2] == b"\xff\xfe", "BOM 不是 UTF-16 LE"
t = b[2:].decode("utf-16-le")
replacements = [
    ('VIProductVersion "1.2.0.0"', 'VIProductVersion "1.3.0.0"'),
    ('VIAddVersionKey /LANG=2052 "FileVersion" "1.2"',
     'VIAddVersionKey /LANG=2052 "FileVersion" "1.3.0.0"'),
    ('"DisplayVersion" "1.2"', '"DisplayVersion" "1.3"'),
]
for old, new in replacements:
    assert t.count(old) == 1, f"命中次数异常：{old}"
    t = t.replace(old, new)
p.write_bytes(b"\xff\xfe" + t.encode("utf-16-le"))
```

不要添加 `-*- coding: ... -*-` 声明：NSIS 3.13 会按声明编码读取脚本，与 UTF-16 不符时报 `Bad text encoding`。`Installer.nsi` 中「1.2 及更早版本登记在 Programs\DesktopNook」是历史兼容说明，版本升级时**保留不改**。

版本说明放在 `native/releases/v1.3.0.md`，纯文本中文，作为 Release 正文上传。除功能变化外，应写明旧版本用户的升级路径（见第 7 节）。

## 4. 打包步骤

### 4.1 构建单文件程序

```powershell
pwsh -NoProfile -File native/scripts/Build.ps1
```

脚本依次执行 `Make-Icon.ps1`（刷新多尺寸 ICO）、核心检查（33 项）、`dotnet publish -r win-x64 --self-contained true -p:PublishSingleFile=true`，输出 `native/artifacts/win-x64/TomatoDesktop.exe`。已跑过核心检查时可加 `-SkipTests`。

### 4.2 生成安装包

```powershell
makensis /V2 `
  "/DPAYLOAD=C:\...\native\artifacts\win-x64\TomatoDesktop.exe" `
  "/DOUTPUT=C:\...\native\artifacts\TomatoDesktop-Setup.exe" `
  native/scripts/Installer.nsi
```

`/DPAYLOAD` 与 `/DOUTPUT` 必须传绝对路径，省略时使用脚本默认值。安装包为当前用户安装。首页可直接填写路径或点「浏览」。受保护的目录需要当前账户的管理员授权。默认程序位置为 `%LOCALAPPDATA%\TomatoDesktop`，覆盖升级预填上次登记的位置，程序和 Data 文件夹都在选择的目录里。换目录后首次打开时会迁入旧数据。静默安装可用 `/S /D=完整路径` 指定目录，`/D=` 放在命令末尾，路径含空格时也无需给整个参数加引号。

安装器采用 zlib 压缩自包含单文件，覆盖升级直接用旧 EXE 执行 `--maintenance=stop`。安装结束前写入导航窗格入口并创建快捷方式，快速访问固定及其诊断在应用启动后后台执行。

生成后核对两个产物的版本资源与哈希：

```powershell
$exe   = (Resolve-Path native/artifacts/win-x64/TomatoDesktop.exe).Path
$setup = (Resolve-Path native/artifacts/TomatoDesktop-Setup.exe).Path
$e = [Diagnostics.FileVersionInfo]::GetVersionInfo($exe)
$s = [Diagnostics.FileVersionInfo]::GetVersionInfo($setup)
"$($e.ProductName) / $($e.FileVersion)  vs  $($s.ProductName) / $($s.FileVersion)"
(Get-FileHash -LiteralPath $setup -Algorithm SHA256).Hash.ToLowerInvariant()
```

要求：`ProductName` 均为「番茄桌面」，`FileVersion` 前三段一致；记录安装包 SHA-256，后续要与 GitHub 返回的 `digest` 比对。

## 5. 发布 Release

### 5.1 标准路径：`Publish-Release.ps1`

```powershell
pwsh -NoProfile -File native/scripts/Publish-Release.ps1 `
  -Executable native/artifacts/win-x64/TomatoDesktop.exe `
  -Installer  native/artifacts/TomatoDesktop-Setup.exe `
  -NotesFile  native/releases/v1.3.0.md
```

脚本行为（源码第 1–87 行）：

1. 校验两个 EXE 的 `ProductName` 与 `FileVersion` 一致，取三段版本生成 `tag = v1.3.0`。
2. 在 `native/artifacts/github-release/v1.3.0/` 暂存安装包与 `SHA256SUMS.txt`，计算本地哈希。
3. 通过 `gh` 确认仓库存在，读取 Release 列表：无同名则创建**草稿**并上传两个文件；已有草稿则只续传缺失资产；**已公开的同名版本直接报错拒绝覆盖**。
4. 逐个比对 GitHub 返回的 `asset.digest` 与本地 `sha256:` 值，不一致则保留草稿不公开。
5. 校验通过后 `gh release edit --draft=false --latest`，公开为最新版本。加 `-VerifyOnly` 只做核验不改状态。

默认仓库为 `chenmo02/tomato-desktop`（`Publish-Release.ps1` 的 `Repository` 参数）；改变发布仓库时必须同步修改 `OnlineUpdater.Repository`，否则客户端的 `TrustedUrl` 会拒绝新地址。脚本**不提交源码**，也不创建 Git 提交，见第 8 节。

### 5.2 备用路径：无 `gh` 时用 REST API

v1.3.0 发布时本机没有 `gh`，GitHub CLI 便携包又因代理对下载域名返回 502 无法获取，因此用 REST API 复刻了完全相同的流程：草稿 → 上传 → digest 校验 → 公开 → latest。以下脚本可直接复制执行（Python 3，凭据只在内存中）：

```python
import subprocess, os, json, urllib.request, urllib.error, hashlib
from pathlib import Path

repo, tag = "chenmo02/tomato-desktop", "v1.3.0"   # tag = v + FileVersion 前三段
setup = Path("native/artifacts/TomatoDesktop-Setup.exe")
notes = Path("native/releases/v1.3.0.md").read_text(encoding="utf-8")

env = dict(os.environ, GIT_TERMINAL_PROMPT="0", GCM_INTERACTIVE="Never")
out = subprocess.run(["git", "credential", "fill"],
                     input="protocol=https\nhost=github.com\n\n",
                     text=True, capture_output=True, env=env, timeout=20).stdout
token = {l.split("=", 1)[0]: l.split("=", 1)[1]
         for l in out.splitlines() if "=" in l}["password"]
H = {"User-Agent": "DesktopNook-Release", "Authorization": "Bearer " + token,
     "Accept": "application/vnd.github+json", "X-GitHub-Api-Version": "2022-11-28"}

def api(url, method="GET", body=None, ctype=None, timeout=120):
    headers = dict(H)
    if ctype: headers["Content-Type"] = ctype
    data = json.dumps(body, ensure_ascii=False).encode() if isinstance(body, (dict, list)) else body
    req = urllib.request.Request(url, data=data, headers=headers, method=method)
    try:
        with urllib.request.urlopen(req, timeout=timeout) as r:
            return r.status, json.load(r)
    except urllib.error.HTTPError as e:
        return e.code, json.loads(e.read().decode("utf-8", "replace"))

base = f"https://api.github.com/repos/{repo}"
_, releases = api(base + "/releases")
draft = next((r for r in releases if r["tag_name"] == tag), None)
if draft and not draft["draft"]:
    raise SystemExit("该版本已公开，不可覆盖；请 bump 到新版本")
if not draft:
    s, draft = api(base + "/releases", "POST", {
        "tag_name": tag, "name": "番茄桌面 " + tag[1:], "body": notes,
        "draft": True, "prerelease": False})
    assert s == 201, draft
rid = draft["id"]

stage = Path("native/artifacts/github-release") / tag
stage.mkdir(parents=True, exist_ok=True)
digest = hashlib.sha256(setup.read_bytes()).hexdigest()
files = {"TomatoDesktop-Setup.exe": setup.read_bytes(),
         "SHA256SUMS.txt": (digest + "  TomatoDesktop-Setup.exe\n").encode()}
_, rel = api(base + f"/releases/{rid}")
for name, data in files.items():
    (stage / name).write_bytes(data)
    if any(a["name"] == name for a in rel["assets"]):
        continue   # 断点续传：跳过已上传资产
    s, r = api(f"https://uploads.github.com/repos/{repo}/releases/{rid}/assets?name={name}",
               "POST", data, "application/octet-stream", timeout=600)
    assert s == 201, r

_, rel = api(base + f"/releases/{rid}")
for name in files:
    a = next(x for x in rel["assets"] if x["name"] == name)
    local = "sha256:" + hashlib.sha256((stage / name).read_bytes()).hexdigest()
    assert a["digest"] == local and a["size"] == (stage / name).stat().st_size, name
s, pub = api(base + f"/releases/{rid}", "PATCH",
             {"draft": False, "prerelease": False, "make_latest": "true"})
assert s == 200, pub
print(pub["html_url"])
```

要点：资产上传必须用 `uploads.github.com`，`api.github.com` 的同一路径返回 404；44 MB 资产在本次网络下耗时约 4 分钟，`timeout` 需放宽；草稿失败可重跑，脚本会自动跳过已上传资产。

### 5.3 发布后核对

读取 `GET /repos/{repo}/releases/latest`，按客户端规则逐项核对（本次 7/7 通过）：

| 规则 | 对应代码 |
| --- | --- |
| 非草稿、非预发布 | `Parse` |
| tag 可解析且严格高于当前版本 | `Parse` → `Normalize` |
| 存在名为 `TomatoDesktop-Setup.exe` 的资产 | `Parse` |
| `digest` 为 `sha256:` + 64 位十六进制 | `Parse` |
| `0 < size <= 512 MB` | `Parse` |
| HTTPS、`github.com`、默认端口、路径前缀 `/{repo}/releases/download/` | `TrustedUrl` |
| 下载完成后 EXE `FileVersion` 三段与 tag 一致、SHA-256 与 digest 一致 | `DownloadAsync` |

再运行 `--verify-online-update <报告目录> <单文件 EXE> --live` 做端到端验证：程序读取真实 Release、下载完整安装包并比对哈希。注意该命令下载约 44 MB，在网络较慢时需要数分钟。

## 6. 客户端为什么可能不提示更新

- **版本未递增**：`Parse` 在 `version <= current` 时返回 `null`。例如线上 `v1.2` 与本机 `1.2` 相同，会显示「已是最新版本」。
- **旧版本客户端未启用在线检查**：1.2 及更早版本的 `OnlineUpdater.Repository` 为空，`Enabled=false`，启动后根本不发起请求。它们**无法通过在线更新升级到 1.3**，必须下载安装包覆盖安装一次，或使用「更多 → 从本地文件更新…」选择安装包；完成 1.3 安装后，后续版本才能走在线更新。`v1.4.0` 发布后，1.3 客户端的后台检查与手动检查都会看到更新提示。
- **后台检查只提示、不自动安装**：启动时检查结果仅写入状态栏与菜单文案，需用户手动进入更新窗口。
- **沙箱自检跳过联网**：`App.IsSandbox` 为 true 时不执行后台检查，属预期行为。

## 8. 源码提交与标签

`Publish-Release.ps1` 与 REST API 路径都只处理发行文件，不会自动提交源码。创建 Release 时 GitHub 会自动在默认分支 `master` 的当前 HEAD 上打 tag；如果本地改动尚未推送，tag 指向的仍是旧版本源码，与 Release 中的二进制不一致。

正确顺序应为：**先提交并推送版本改动，再发布**。v1.3.0 发布时工作区仍有未提交改动（csproj、NSIS、更新窗口、文档等），因此 tag `v1.3.0` 指向远端 `master` 的旧提交；v1.4.0 发布时工作区同样未提交，tag `v1.4.0` 也指向旧提交。后续需要补齐提交，或在新版本发布时确保先推送。仓库为公开仓库，提交前请确认改动内容。

`v1.5.1` 起已按正确顺序执行：先把全部版本改动提交为 `a1da474` 并推送 `master`，再由 REST API 创建 Release；`git ls-remote --tags` 确认 `v1.5.1` 指向 `a1da474`，与安装包版本资源一致。发布后追加的文档记录单独提交，不改变 tag 指向。`v1.5.2` 同此顺序：版本改动提交为 `6ef5d67` 并推送后创建 Release，由 `GET /git/ref/tags/v1.5.2` 确认 tag 指向该提交。

## 9. 故障排查

| 现象 | 原因 / 处理 |
| --- | --- |
| `gh: 无法将“gh”项识别为 cmdlet` | 本机未安装 GitHub CLI；安装并登录，或改用第 5.2 节 REST API |
| `uploads.github.com` 根路径探测 502 / 超时 | 不代表上传不可用；用实际 `POST .../assets?name=` 验证。本次根路径 HEAD 失败但上传 201 |
| `github.com` 主站请求超时 | 检查 `releases/download/` 是否重定向到 `release-assets.githubusercontent.com`；客户端下载走该重定向，v1.3.0 发布时返回 206 |
| 下载时 `RemoteDisconnected` / 代理端口拒绝连接 | 本机代理进程异常。`api.github.com` 直连仍可读取发布记录与资产 digest；客户端在线更新需能访问 `github.com` 的 `releases/download/` 重定向域名，网络恢复后重试 |
| NSIS 报 `Bad text encoding` | `Installer.nsi` 编码被改坏或加了 coding 声明；恢复 UTF-16 LE BOM + CRLF |
| 发布脚本报「程序与安装包版本或产品标识不一致」 | `csproj` 与 `Installer.nsi` 的 `FileVersion` 不同步，或 `ProductName` 不是「番茄桌面」 |
| 客户端报「发布文件缺少有效的下载地址、大小或 SHA-256 校验信息」 | 资产缺 `digest` / `size` 越界 / URL 不属于本仓库 `releases/download/` 路径 |
| 客户端报「更新程序版本与发布记录不一致」 | tag 三段与 EXE `FileVersion` 三段不一致 |
| 脚本报「该版本已公开」 | 不覆盖已发布文件；bump 到新版本号重发 |
| 草稿残留 | 重跑脚本或 API 脚本会跳过已上传资产并续传；也可在 GitHub 删除草稿 |
| 大资产上传写超时（v1.5.2 的 71 MB） | Python urllib 经代理 POST 大 body 触发 `The write operation timed out`，服务端未收到文件；改用 curl `--http1.1 -H "Expect:" --data-binary @文件`，加 `--speed-time/--speed-limit` 快速失败，重跑前先读草稿资产跳过已上传项。实测 161.3 秒 / 约 440 KB/s 上传成功 |
| `git ls-remote --tags` 报 `schannel: server closed abruptly` | 本机代理对 git 的 TLS 连接不稳定；改用 `GET /repos/{repo}/git/ref/tags/{tag}` 读取 `object.sha` 核对 tag 指向 |
| 已公开版本需要撤回 | 删除 Release 不会自动删除 tag，且客户端可能短暂读到缓存；稳妥做法是发布更高的修正版本 |
